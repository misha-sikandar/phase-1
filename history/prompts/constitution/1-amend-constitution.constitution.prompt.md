```text
# Todo Evolution – Project Constitution

## Preamble
This Constitution governs how the **Evolution of Todo** project is designed, specified, implemented, reviewed, and evolved across all five hackathon phases. The intent is to practice **Spec-Driven, AI-Native Software Development**, where humans define *what and why* through specifications and architecture, and AI agents generate *how* through implementation.

This document is binding across **all phases**. Any implementation that violates this Constitution is considered **non-compliant**, regardless of functional correctness.

---

## 1. Core Philosophy

### 1.1 Spec-Driven Development (SDD)
- All development **must begin with written specifications**.
- Specifications define **behavior, constraints, interfaces, and acceptance criteria**.
- Code is a *derived artifact* generated from specs, not the primary source of truth.
- When behavior is incorrect, **the spec is updated**, not the code.

### 1.2 AI-Native Development
- AI agents (Claude Code, OpenAI Agents) are **first-class contributors**.
- The human role is **system architect and spec author**, not syntax writer.
- AI agents must be guided through:
  - Constitutions
  - Feature specifications
  - Architectural constraints

### 1.3 Progressive System Evolution
The system evolves intentionally through increasing architectural complexity:
1. Single-process CLI
2. Client–server web application
3. AI-agent mediated system
4. Cloud-native container orchestration
5. Event-driven distributed architecture

Each phase must **build upon**, not replace, the previous phase's conceptual model.

---

## 2. Absolute Rules (Non-Negotiable)

### 2.1 No Manual Coding
- ❌ Humans may **not** write production code by hand.
- ✅ All production code **must be generated by Claude Code**.
- Humans may:
  - Write specifications
  - Write constitutions
  - Write documentation
  - Refine prompts

If any line of code is manually written, the phase is **invalid**.

### 2.2 Specification-First Enforcement
- No implementation may begin without an approved spec.
- Each feature must have:
  - A Markdown specification file
  - Clear acceptance criteria
  - Defined inputs and outputs

### 2.3 Single Source of Truth
- Specifications override code.
- README explains usage, **not behavior**.
- Behavior changes require spec changes.

---

## 3. Repository Governance

### 3.1 Required Files
Every phase must include:
- `Constitution.md`
- `CLAUDE.md`
- `/specs` directory with phase-relevant specs
- `/specs/history` or versioned spec updates

### 3.2 Monorepo Discipline
- Frontend and backend live in the same repository.
- Shared specs apply across all services.
- No duplicated business logic across services.

### 3.3 Traceability
Every implemented feature must be traceable to:
- A spec file
- A Claude Code prompt
- A generated output

---

## 4. Phase-Specific Architectural Laws

### 4.1 Phase I – Console Application
- In-memory storage only
- No persistence
- Deterministic behavior
- Single-process execution

### 4.2 Phase II – Web Application
- Stateless backend
- Persistent storage via database
- RESTful APIs only
- Authentication enforced via JWT

### 4.3 Phase III – AI Chatbot
- AI agent **never** accesses the database directly
- All side effects occur via MCP tools
- Chat endpoint is stateless
- Conversation state is persisted externally

### 4.4 Phase IV – Kubernetes Deployment
- All services must be containerized
- Configuration via environment variables
- No hard-coded secrets
- Deployable via Helm charts

### 4.5 Phase V – Event-Driven Architecture
- Inter-service communication via events
- Kafka (or equivalent) as event backbone
- Dapr abstracts infrastructure dependencies
- Services must be independently deployable

---

## 5. AI Agent Governance

### 5.1 Claude Code Usage
Claude Code must:
- Read relevant specs before implementation
- Follow architectural and stylistic constraints
- Avoid adding features not present in specs

### 5.2 OpenAI Agents
- Agents are **goal-driven**, not chat-driven
- Tools define the agent's capabilities
- Agents must explain actions in natural language

### 5.3 MCP Tool Contract
- MCP tools are the **only interface** between AI and system state
- Tools must be:
  - Stateless
  - Deterministic
  - Explicitly specified

---

## 6. Cloud-Native Principles

### 6.1 Statelessness
- Application services must not store in-memory state across requests.
- Horizontal scaling must be safe.

### 6.2 Configuration
- Environment-based configuration only
- Secrets via secret managers or Kubernetes Secrets

### 6.3 Observability
- Logs are structured
- Errors are explicit
- Failures are explainable

---

## 7. Event-Driven Discipline (Phase V)

- Events represent **facts**, not commands
- Consumers must be idempotent
- Event schemas are versioned
- No synchronous coupling between producers and consumers

---

## 8. Quality Standards

### 8.1 Code Quality (AI-Generated)
- Clear module boundaries
- Descriptive naming
- No dead code
- No speculative features

### 8.2 Documentation Quality
- Specs are human-readable
- Examples are concrete
- Assumptions are explicit

---

## 9. Evaluation Alignment

This Constitution is designed to maximize:
- Hackathon scoring
- Real-world architectural correctness
- AI-native system thinking

Judges are expected to evaluate:
- Adherence to this Constitution
- Spec clarity and evolution
- Architectural maturity
- Effective AI utilization

---

## 10. Amendment Process

This Constitution may be amended **only by adding a new version section** at the end of the document.

Amendments must:
- State rationale
- Preserve backward compatibility where possible

---

## Final Declaration

By proceeding with this project, the author commits to:
- Architecting systems, not writing code
- Letting specifications drive reality
- Treating AI as a collaborative engineer

**This Constitution is binding across all phases of the Evolution of Todo project.**
```
